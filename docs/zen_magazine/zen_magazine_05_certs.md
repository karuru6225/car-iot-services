# GitHub Actions でファームウェア更新しようと思ったら、量産の常識にたどり着いた

## 言いたいこと

車載 ESP32 を AWS IoT Core につないでいます。MQTT over TLS なので、証明書は1台ごとに違います。

その証明書を、私は**セキュリティを考えて**ファームから外したのではありません。**GitHub Actions でファームウェア更新を自動化したかったから**、外すしかありませんでした。タグを push して1つのバイナリを作り、公開 URL から全台へ配る。そう決めた時点で、個体ごとに違うものはバイナリに入れられません。

出来上がった形をあとで調べたら、量産 IoT の定石でした。動機は違うのに同じ場所に着いた、という話です。

- 置き場所を決めたのは、セキュリティではなく **配布方法**
- 個体情報は **キッティングで後入れ**する。OTA では触らない
- MAC から鍵を作ろうとして捨てた話も添えます

受信経路や基板の話は不要です。OTA のバイナリに何を載せてよいか、だけ押さえておけば読めます。

---

## やりたかったこと：タグ push で配る

USB で書くたびに車へ取りに行く開発は続きません。やりたかったのは **OTA** です。有線で繋いで更新するのではなく、無線通信でファームウェアを更新することです。流れは次の一本です。

`vX.Y.Z` を push する → Actions が PlatformIO でビルドする → `firmware.bin.gz` を S3 に置く → AWS IoT Jobs を作る → 端末が次に起きたときに拾って更新する。

AWS 認証はアクセスキーではなく **OIDC** です。配信先は Thing グループ（基板シリーズごと）で絞ります。ファームの URL はジョブドキュメントに入り、端末は HTTPS で取りにいきます。

ここまでを成立させると、配布物は **全台同じバイナリ** になります。公開バケットから落とすので、中に秘密を置けません。

---

## それが禁じること

デバイス証明書・秘密鍵・MQTT エンドポイントを `#define` やソースに焼く案は、最初から割れます。

- Actions が作る成果物が個体ごとに分岐する
- 公開 URL のバイナリに秘密鍵が載る
- 「1種類のファームを配る」OTA が、キッティングと同じ作業になる

`device_id` もファームに焼きません。Thing 名は MAC から `esp32-gw-<mac>` と決めていて、MAC はキッティング時に読むだけです。個体差は **フラッシュの別領域** に残します。

ESP32 のフラッシュは、用途ごとに切れます。この記事で使う名前だけ先に置きます。

- **app0 / app1** — 動かすファーム本体の席が2つあります。片方で動きながら、もう片方に新しいバイナリを書いて切り替えます。失敗したら席を戻せます
- **SPIFFS** — その隣にある小さなファイルシステムです。`/certs/device.key` のようにパスを付けて置けます
- **NVS** — キーと値の設定置き場です。MQTT ホストのような短い個体情報向きです
- **OTA** — 有線で繋いで更新するのではなく、無線通信でファームウェアを更新することです。ここでは LTE 経由で HTTPS 取得し、空きスロット（app0 / app1）へ書きます

| 何 | どこ | いつ書く |
| --- | --- | --- |
| CA / デバイス証明書 / 秘密鍵 | SPIFFS（`/certs/`） | キッティング |
| MQTT ホスト、基板バージョン | NVS | キッティング |
| アプリ本体 | app0 / app1 | 量産書き込みと OTA |

OTA は app スロットだけを入れ替えます。SPIFFS と NVS は残るので、更新のたびに証明書を配り直さなくてよい、という分け方です。起動時にモデムへ証明書を載せる処理はありますが、ソースはフラッシュ上のファイルであって、ファームの定数ではありません。

---

## だからキッティングで後入れする

手順は `ops/provision_device.ps1` にまとめています。PC に USB でつなぎ、1台ずつです。

1. `esptool` で MAC を読む → Thing を作る → OTA 用 Thing グループへ入れる
2. `aws iot create-keys-and-certificate` で証明書を発行し、Policy を付ける
3. 秘密鍵つきの `provision_config.h` を **ローカルだけ**に生成する（gitignore、書き込み後に削除）
4. `provision` env の専用ファームを書いて起動させる。中身は SPIFFS / NVS へ書いて終わるだけ
5. そのあと本番ファームを書く。本番ファームには個体情報は入っていない

専用ファームを挟むのは、PC から SPIFFS や NVS へ直接書き込む手段が、なぜか動かなかったからです。デバイス上の小さなプログラムに書かせる方が確実でした。`provision_config.h` には秘密鍵が入るので、生成・フラッシュ・即削除までをスクリプトに閉じます。Actions の成果物や GitHub Release には載せません。

手作業です。自分一人しか使っていないので、手動キッティングでも回っています。

ここまで来てから知ったのですが、この「ファームは全台共通、個体情報は別の領域」は量産では普通の形でした。Espressif の製造向けドキュメントも、[証明書をファームに埋め込むのをやめて、工場で書いた専用領域から読む](https://docs.espressif.com/projects/esp-jumpstart/en/latest/esp32/manufacturing.html)形を勧めています。私は CI の都合で同じところに出ただけです。

## 危なかった案：MAC から鍵を作る

キッティングを楽にしたくて、最初に考えたのは「MAC アドレスから鍵を決まった手順で導出する」案でした。事前登録した MAC の分だけサーバー側に証明書を用意しておけば、1台ずつ個体情報を書く作業が消えます。

実装する前に捨てました。ESP32 の MAC は先頭のベンダー部分が固定で、残りは実質 24bit 程度しかありません。しかも Wi-Fi や BLE のパケットに平文で乗って飛んでいます。こちらの `device_id` 自体が `esp32-gw-<mac>` なので、そもそも公開情報です。

秘密鍵の材料が誰にでも読める、という設計です。MAC を拾えば鍵を再現できます。もちろんそんな怖いことはしたくないので却下しました。

## その先：Fleet Provisioning（未実装）

台数が増えると、USB を1台ずつつなぐ作業の方が先に破綻します。量産されたときどうなるか興味があったので、AWS IoT の [Fleet Provisioning](https://docs.aws.amazon.com/iot/latest/developerguide/iot-provision.html) について軽く調べました。

候補は2つです。

- **by Claim** — 極小権限の claim 証明書を全台に焼き、起動時にデバイスが鍵ペアを作って CSR を出す。キッティングの USB 作業を消せる。claim が漏れると新規登録を止めない限り悪用され続ける
- **by Trusted User** — 作業者が5分だけ有効な一時 claim を取り、デバイスに渡す。恒久的な共有秘密をファームに残さない。ただし「PC に1台つなぐ」手間は今と近い

今の目的は「Actions で同じバイナリを配る」なので、claim をファームに焼く by Claim は、また「共通ファームに何を載せてよいか」問題に戻ります。載せてよいのは **本番のデバイス秘密鍵ではない** ことだけは、今の設計と同じです。

---

## まとめ

証明書をどこに置くかは、**誰のバイナリをどこから配るか**が決めていました。「タグ push で全台に配る」を先に決めたので、個体情報の置き場は自動的にファームの外になり、キッティングは後からついてきた手順です。

Fleet Provisioningは興味深いですが、一人で使う個人的な基板なので採用はしないと思います。
