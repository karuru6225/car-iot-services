# 車のバッテリー上がり対策に、車載 IoT を自作した話③ インフラ編

## 言いたいこと

インフラは「デバイスが動いてから」ではなく、**MVP とほぼ同時に立ち上げました**。
git の最初の「最低限が一通り動いた」コミットに、既製品ファーム・Terraform・Web がまとめて入っています。

この編で言いたいのは次です。

- 測って送る側と受ける側を、同じタイミングで通した
- デバイスとの接点は **AWS IoT Core** に集約（Topic Rule / Shadow / Jobs）
- いまのデータ閲覧の本命は `web/index.html` ではなく、**別プロジェクトの EC2＋Docker 上の Grafana**
- Athena は置き方を雑にするとすぐ高い。パーティションとクエリを意識する

シリーズは3本です。Terraform / Athena / Grafana まわりだけ欲しい人は、この編だけでも大丈夫です。

## MVP と同じタイミングでクラウドも作る

受信側は Terraform です。流れはこうです。

```text
デバイス（MQTT over TLS）
  → AWS IoT Core
  → Rule → Lambda(ingest) → S3（年月日時でパーティション）
  → Glue + Athena
  →（見るのは主に Grafana。初期は Web も用意した）
```

「デバイスが完璧になってからクラウド」だと、経路のバグを後半に持ち越します。
逆にクラウドだけ先でも、実データがないと運用の感触が分かりません。
なので私は、測って送る側と受ける側を同じタイミングで通す方針にしました。

立ち上げ直後の数日で Cognito や削除 UI なども足しました。
MVP 機から実データを流し、DeepSleep（数分おき）でも「とりあえず見える」ことを確認できたので、そのあとハードとファーム（①②）に集中できました。

AWS IoT まわりの詳細は次の章です。

## AWS IoT でやっていること

デバイスとの接点は、ほぼ **AWS IoT Core** に集約しています。
Terraform で Policy や Topic Rule を置き、Thing と証明書はキッティングスクリプトで発行、という分担です。

### テレメトリは Topic Rule → Lambda

デバイスは `sensors/{device_id}/data_bin` に MessagePack を publish します（②で短くしたやつ）。
IoT Core の Topic Rule がこれを拾い、Lambda `ingest` に渡して S3 へ書き込みます。

```sql
SELECT encode(*,'base64') AS payload, topic(2) AS device_id
FROM 'sensors/+/data_bin'
```

バイナリのままだと Rule から Lambda に渡しにくいので、**base64 にしてから渡す**形にしています。
Lambda 側で decode して S3 にはフルネームの JSON で保存するので、Glue / Athena はいじらなくて済みます。

MVP 当時は JSON トピック `sensors/+/data` もありましたが、いまの本命は `data_bin` です。

### Device Shadow で設定をやりとり

測定値の送信とは別に、デバイス設定は **Device Shadow** で持っています。

- **reported** — デバイスが起動時に現在値を報告（`ah_offset`、充電閾値、`fw_version` など）
- **desired** — クラウドから更新 → デバイスが次回起床時に delta を受け取り NVS へ適用

車のそばでは OLED メニュー、遠くからは管理画面や Admin API 経由で Shadow を触ります。
「グラフで眺める」と「閾値を変える」は導線が分かれています（Grafana は後述）。

### IoT Jobs で OTA とコマンド

OTA とリモートコマンド（Ah リセット、充電指示など）は **IoT Jobs** です。
②で詳しく書きましたが、インフラ側のポイントだけ言うとこうです。

- ジョブはオフライン中もキューに残る → DeepSleep 端末は次の起床時に拾う
- OTA 配信対象は Thing グループ `ota-target-car-iot-gw` で絞る（キッティング後に手動で追加）
- ファーム本体は **公開 S3** から HTTPS で落とす（証明書はファームに含めない②の設計）

Jobs は「指示を届ける箱」、実際のバイナリ取得は S3、という分担です。

### 骨格と運用機能は別タイミングで足した

MVP 時点で通したのは **Topic Rule + ingest** だけです。「MQTT で送って S3 に入る」経路の確認が先でした。

そのあと②の OTA／キッティング前提で、次を足しています。

- Device Shadow
- IoT Jobs
- ファーム配布用の公開 S3
- OTA 対象の Thing グループ

「データが流れる骨」と「車載本番の運用機能」はレイヤが違う、という感じです。

## index.html は今ほとんど見ていない

MVP 当時は Chart.js の `web/index.html` も一緒に作りました。経路検証には使いましたが、**いまはほぼ使っていません**。

日々の電圧・電流・Ah は、**別プロジェクトで用意している EC2 上の Docker Grafana** に Athena を足して見ています。
EC2＋Docker にしているのは、ECS などより **コストが安く済みそうだったから**です。個人用途の常駐ダッシュボードなら、この方が収まりやすい印象でした。

閾値変更などはまだ API／管理画面側（Shadow／Jobs）を使います。「見る」と「触る」で導線が分かれた、ということです。

---

## Athena のコストは侮れない

Grafana × Athena のクエリが荒く、**スキャン量が嵩んで請求が目立った**時期がありました。
パーティション条件を見直し、ダッシュボードの更新頻度も抑え、いまは様子見です。

Athena は「置いただけ」だと簡単に高くなります。
year/month/day/hour のパーティションを効かせることと、無駄打ちしないことが大事でした。
「見えるダッシュボード」を作った瞬間に、裏でフルスキャンが走っていないか疑った方がいいです。

ちなみに、アラートのため Grafana Alerting から毎回 Athena を叩く案は、コストと可用性の両方で見送りました。

### これから

ingest は MQTT 1通あたりおおよそ1ファイルなので、小ファイルが増えやすいです。
**1時間おきに compaction（結合）する**つもりです。スキャン効率とコストの両方を取りたいです。

バッテリー上がりアラート（閾値→SNS）などもバックログにあります。

## シリーズまとめ

メインバッテリー上がりから始めて、だいたいこの順でした。

1. MVP と Terraform を **同時に**通す  
2. 基板を自作し、試作で桁ミスを知る（①）  
3. OTA とキッティングで車まで行かない開発にする（②）  
4. Grafana で眺め、Athena コストを直す（③）  

特に効いたのは、**最初から送る／受けるをセットで通したこと**と、**取りに行かなくて済む OTA** だと思います。

売りは **一気通貫**です。一方で車載でここまで全部やる人は多くないので、記事は分野ごとに分けました。基板でも OTA でも Athena でも、どこか一つでも役立てばうれしいです。
