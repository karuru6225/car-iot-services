# 車のバッテリー上がり対策に、車載 IoT を自作した話③ インフラ編

## このシリーズについて

車のメイン／サブバッテリーを Cat-M（SORACOM）経由で AWS IoT に送り、遠隔で監視・設定する自作 IoT の記録。売りはハード〜ファーム〜クラウドの一気通貫。記事は分野ごとに 3 本に分けている。

| # | 編 | 内容 |
| --- | --- | --- |
| ① | 基板設計・作成編 | 動機・MVP・専用基板・試作／再設計・筐体 |
| ② | ファームウェア開発編 | 計測サイクル・OTA・キッティング・GHA |
| ③ | **本編** | Terraform・Grafana・Shadow／Jobs・運用コスト |

日常の閲覧は別プロジェクトの Grafana（EC2 上 Docker）。閾値変更などは Device Shadow / IoT Jobs。  
M5Stack の MVP と **ほぼ同時に**立ち上げた受信側と、いまの運用・これから、をまとめる。

---

## MVP と同時にインフラを立ち上げる

履歴を見ると、最初の「最低限が一通り動いた」コミットに、`m5atom_iot_gateway`（既製品 MVP）と `infra/`（Terraform）、`web/index.html` がまとめて入っている。
**デバイス先行でもクラウド先行でもなく、測って送る側と受ける側を同じタイミングで組んだ**、というのが実態だ。

受信側の骨組みは Terraform で管理している。構成はだいたい次のとおり。

```text
デバイス（MQTT over TLS）
  → AWS IoT Core
  → Topic Rule → Lambda(ingest) → S3（raw/year=/month=/day=/hour=/）
  → Glue + Athena
  →（閲覧は後述の Grafana。初期は API Gateway + CloudFront の Web も用意）
```

立ち上げ直後の数日で、Cognito 認証やカスタムドメイン、削除 UI、権限（admin / viewer）なども足していった。MVP 機から実データを流し、Athena でグラフが引けること、DeepSleep サイクル（数分おき）でも取りこぼしが目立たないことを確認できた。

この「経路が通った」状態が先にあったから、あとから専用基板や本格ファーム（①・②）に集中できた。

のちに、②で書いた OTA / キッティング前提に合わせて足したものもある。

- IoT Device Shadow（設定の reported / desired）
- IoT Jobs（OTA・コマンド）
- ファーム配布用の公開 S3 バケット
- Thing グループによる OTA 対象管理

MVP 時点の骨と、車載本番向けの運用機能はレイヤが違う、という感じ。

## 管理画面（初期）と remote 操作

MVP 当時は計測の閲覧用に `web/index.html`（Chart.js、CloudFront 配信）も一緒に作った。API Gateway + Athena でグラフを出す経路の検証には使ったが、**いまはほぼ使っていない**。

日々の電圧・電流・Ah などは次節の Grafana 側で見ている。

一方、運用パラメータの変更は Web / API 経由が残っている。**Device Shadow の desired** と **IoT Jobs** で変える。管理者向け（`web/admin.html`、Cognito の `admin` グループ）ではだいたい次ができる。

| 操作 | 経路 |
| --- | --- |
| デバイス一覧 + 最新 reported | `GET /admin/devices` |
| 充電開始 / 停止閾値などの更新 | `PUT /admin/shadow/{id}`（desired） |
| Ah リセット・充電開始などのコマンド | `POST /admin/command/{id}` → IoT Jobs |
| OTA 対象グループへの所属変更 | `PUT /admin/groups/{id}` |

Shadow で見ている代表項目は、`chg_start_v` / `chg_stop_v` / `ah_offset` / `fw_version` / 充電中フラグなど。
デバイスは次回起動時に delta を受け取り NVS に反映する。
「手元に行かなくても閾値を触れる」状態は、車載 IoT の体験としてかなり効く。

## Grafana で可視化

日々のダッシュボードは、**別プロジェクトで立てている EC2 上の Docker で動く Grafana** を使っている。
そこにこのシステムの Athena をデータソースとして足し、S3 に溜まった時系列（電圧・電流・電力・Ah・温度など）を眺めている。

ちなみに EC2 上で Docker を動かしているのは、ECS などより **コスト的に有利だったから**。個人用途の常駐ダッシュボードなら、この構成の方が安く収まりやすかった。

`web/index.html` は経路検証用の初期 UI、本番の「見る」導線は既存 Grafana に寄せた、という役割分担になった。

## 現状と今後

### いまやっていること

Grafana × Athena のクエリが荒く、**スキャン量が嵩んでコストが目立った**時期があった。
クエリ側を見直し（パーティション条件の見直しなど）、いまは様子見中。

Athena は「置いただけ」だと簡単に高くつく。
Hive パーティション（year/month/day/hour）をちゃんと効かせることと、ダッシュボードの更新頻度を抑えることが重要だった。
（アラート用途で Grafana Alerting から毎回 Athena を叩く案は、コストと可用性の両方で不採用にしている。）

### これから

ingest は現状、MQTT 1 通ごとにおおよそ 1 オブジェクトを S3 に書いている。
時間経過とともに **小ファイルが大量に溜まる**ので、Athena の効率が落ちやすい。

計画として、**1 時間おきに、その時間帯の細かいオブジェクトを compaction（結合）する**処理を入れるつもり。
これでスキャン効率と運用コストの両方を改善したい。

そのほかバックログには、バッテリー上がりアラート（ingest 後に閾値判定 → SNS）、ULP 低電圧起動、ストリーミング OTA などが並んでいる。

## おわりに（シリーズまとめ）

メインバッテリー上がりという身近な困りごとから始めて、

1. M5Stack MVP と Terraform 受信基盤を **同時に**立ち上げ、経路を証明する  
2. KiCad / JLCPCB でハードを自前化  
3. 試作で抵抗値の桁ミスに気づき BOM を正す  
4. OTA・キッティング分離を軸にファーム・筐体・CI を回す  
5. Shadow / Jobs / Grafana で運用する  

という順で組んできた。

特に効いたのは、**MVP の段階でデバイスとクラウドをセットで通した**ことと、**車まで取りに行かなくて済む OTA とキッティング分離を早めに入れた**ことだと思う。

売りはあくまで **ハード〜ファーム〜クラウドの一気通貫** にある。一方で、「車載でここまで全部やる人」は多くないので、記事は分野ごとに 3 本に分けた。基板・ノイズ・試作、OTA・キッティング、Terraform・Athena・Grafana——どれか一つの分野でも、どこか役立つ部分があればうれしい。
