# Zenn 向け書き方メモ

目的: 自作シリーズ（`docs/zen_magazine/`）を寄せるときの、**文体・分量・章立て・技術の解説のしかた**の指針。特定記事のコピーではなく「型」の抽出。

調査対象: Zenn 上で反応が大きかった技術記事を複数本横断して傾向をまとめたもの（2026-07 時点）。

文字数の目安（対象記事群）: **約 2,500〜5,600**（中央値おおよそ **3,500**、平均おおよそ **3,700**）。長編チュートリアルではなく、**1トピックを読み切れる長さ**。

---

## 1. 文体

### 基調

- **です・ます調**がほぼ一貫。論文調・である調はほぼ使わない。
- カジュアル寄りだが雑ではない。「〜ですね」「〜じゃないですか」「イマイチ」「モニョモニョ」「コスパ悪すぎ」など口語を適度に混ぜる。
- 一人称は「私」。読者への呼びかけは「〜しましょう」「〜してください」。
- AI やツールを「Copilotくん」「GPTくん」と呼ぶなど、**固い技術の硬さを落とす道具**としてあだ名・絵文字を使うことがある。

### 主張の出し方

- 冒頭か早い段階で **結論／記事の約束** を言い切る。
  - 例:「APIをそのままMCPサーバーにするのは止めてください」
  - 例:「結論を簡単に書くと」（手順もの）
  - 例:「言いたいこと」見出し（ツール併用）
- 体験談型でも、「愚痴が半分、気をつけようが半分」のように **この記事のスタンスを自己定義**する。
- 強いタイトルを使うときは、本文で一度ゆるめる／本音を併記する（「タイトルについて」など）。読者との距離を取りすぎない。

### リズム

- 1文は短め〜中くらい。長文の仕様説明より、**短い断定 → 理由 → 具体** のくり返し。
- 段落は薄く、見出しで区切る。壁の段落を避け、スクショや箇条書きで息継ぎする。

---

## 2. 分量

| 目安 | 内容 |
| --- | --- |
| 本文文字数 | **3,000〜4,500** がスイートスポット。5,500超は論点が多い論説・比較のみ |
| スクリーンショット | 手順もの・障害調査では **多め（4〜8枚）**。論説では 0〜1 でもよい |
| コードブロック | **少なめ**。必要最小限（設定 YAML / 短いコマンド／結果の断片）。長すぎるログは貼らないか要約 |
| 外部リンク | 公式 docs・ブログ・ダッシュボードへ **根拠として即リンク**（読者に検索させない） |

連載や教科書のような「全部説明する」分量ではない。**今日の気づき1つ**にフォーカスする。

自作シリーズへの示唆: 1本あたりも 3〜5 千字前後に収め、詳細はリポジトリ docs や別編へ逃がすと近い。

## 3. 章の分け方

### よくある型（4パターン）

**A. 問題提起 → 調査 → 結論 → 感想／参考**

障害調査・謎 dig（AZ ID など）。

```text
はじめに（疑問をそのまま書く）
→ 結論（すぐ答え）
→ もうちょっと詳しく（公式を要約）
→ 感想
→ 参考
```

**B. 断言 → なぜダメか（問題を分解）→ 望ましい設計 → まとめ**

反パターン指摘（MCP、Agent Skills など）。

```text
断言（1行で分かる主張）
→ 何故ダメか（実害ベース）
→ 問題1 / 2 / 3（各節の末に「望ましい設計」）
→ 対策案（クライアント側など）
→ まとめ
```

**C. 言いたいこと（先）→ 用語ミニ説明 → 手順 → 余談**

How-to／併用 tips。

```text
言いたいこと（または結論を簡単に）
→ 用語の超短い説明（知ってる人は飛ばせる）
→ 準備 → 実際にやってみる（スクショ付き）
→ 思うこと／余談／追記
```

**D. 候補を並べる比較 → 個人的まとめ**

ツール紹介（図の描き方など）。

```text
迷いの共有
→ 選択肢ごと（メリット中心、類似はバッサリ省略と宣言）
→ 個人的なユースケースのまとめ
```

### 見出しの特徴

- 見出し文言が **会話的・結論的**（「〜するな」「〜ってどこ？」「結論」「言いたいこと」「余談」）。
- `##` / `#` の階層は浅く、**深掘りしすぎない**（`####` まで掘る記事は少ない）。
- 手順記事では見出し＝手順のフェーズ名。論説では見出し＝問題のラベル。
- 末尾に **「まとめ」「最後に」「余談」「追記」** のいずれかがほぼ必ずある。時間経過の訂正は「(追記)」で正直に足す。

### 導入の型

ほぼ共通で次のどれか（または併用）:

1. **最近起きたこと**（障害、新機能、高い請求）
2. **迷い・面倒**（毎回手動が面倒、どのツールにすればいいか）
3. **断言**（そのままMCPにするな）
4. **自分の立場**（AWS メインで Azure を触って戸惑った）

導入の直後に「この記事はこういう人向け／こういうスタンス」を短く置くことが多い。

## 4. 技術の解説のしかた

### 詳細度の原則

- **読者が今困っている判断に必要な深さまで**。仕様の網羅はしない。
- 公式ドキュメントは読む前提ではなく、**自分が要約してからリンク**する（「機械翻訳が分かりにくいので要約すると」）。
- 用語説明は短い。「〜って何？」節があっても数段落。詳細は公式へ。
- 「似たツールはバッサリ省く」と宣言してスコープを切る。

### 説明の組み立て

よく使う三段:

1. **実害・体験**（コストが高い、精度が悪い、環境が壊れた、どこが影響か分からない）
2. **メカニズムの最小説明**（なぜそうなるか。トークンが増える、AZ名がアカウントごとにマップされる、など）
3. **望ましい形／やったこと**（手順、設計指針、数字の目安）

数字は印象が残る程度に置く（「説明文は200文字以下」「数千円かかった」など）。精密なベンチ全体にはしない。

### 補足・注釈の加え方

| やり方 | 使いどころ |
| --- | --- |
| 「なお」「ちなみに」の一文 | 設計上のコツを軽く添える（description を環境変数に、など） |
| 「余談」見出し | 本筋から外れるが面白い話 |
| 「追記」パネル／見出し | 仕様変更や読後のアップデート |
| callout／注意の一文 | 「今回取り上げる実装は〜の場合」など前提の限定 |
| 吹き出し的な引用（「👀『…』」） | 読んだ瞬間の違和感を再現して共感を取る |
| 箇条書き | メリット／問題点／チェック項目の列挙 |

補足は **脚注だらけにせず**、本文の流れの中に短く挿すか、章末に隔離する。

### コード・画面の扱い

- 手順は **画面のスクショ中心**。コードは設定の断片だけ。
- 長い JSON／トークン生ログは貼りすぎない（コスト記事でも「定義が長い」ことの説明が主で、全文ダンプではない）。
- 「実際にやってみる」では、成功だけでなく **誤診・例外の扱い**も短く載せ、信頼感を上げる。

### しないこと（傾向）

- API リファレンス級のパラメータ一覧を本文に載せない
- 概念から体系立てて教科書にしない（必要なら「従来のツールとの違い」程度）
- 「詳しくはリポジトリ全読了」を強要しない。リンクは任意の深掘り口

## 5. タイトルの型

反応が大きかったタイトルに共通するフック:

- **命令・禁止**: 「〜するな」「導入してはいけない」
- **疑問**: 「〜ってどこ？」「本当か」
- **得する約束**: 「勝手にレビューしてくれる」「捗る」「料金内で使える」
- **具体名詞**: 製品名・現象名・固有 ID を入れる

抽象タイトルより、**スクロール中に判断できる具体**を優先している。

## 6. 自作シリーズへ寄せるときのチェックリスト

記事を書く／直すときの短いリスト。

- [ ] 冒頭 10 行以内に「この記事で得ること／主張」があるか
- [ ] です・ます＋体験の一人称で、論文調になっていないか
- [ ] 1 本の文字数がおおよそ 3〜5 千に収まるか（超えそうなら編を分ける／詳細を docs へ）
- [ ] 見出しが会話的で、読者がスキップできる単位になっているか
- [ ] 技術説明が「実害 → なぜ → 望ましい形」になっているか
- [ ] 仕様の網羅になっていないか（目安・要約・リンクで十分か）
- [ ] 補足は「なお／余談／追記」に整理されているか
- [ ] スクショや短い具体（数字・画面・1手順）があるか
- [ ] 末尾にまとめ／これから／別編への誘導があるか

## 7. 自作下書きとのギャップ（意識すると寄せやすい点）

現状の `docs/zen_magazine/` 下書きは、このメモの型に比べると:

- **章がやや教科書的**（レイヤ表、ブロック表が厚い）
- **結論や「できること」が後ろ／表寄り**になりがち（型では前に出す）
- **文字数が連載合計で長くなりやすい**（1本あたりは削る余地あり）
- **口語の温度**が控えめ（「めんどくさいから OTA」のような一文が近い温度）

寄せるなら: 各編の導入を「最近困った／やりたい約束」に振り、機能表は残しつつ直後に口語で要約し、回路定数の深掘りはリポジトリ docs へ逃がす、が効きやすい。

---

## 8. 注意

- 文体の模倣は構文・構成の型にとどめ、**内容や固有フレーズのコピーはしない**。
- 反応が大きい記事＝全員向けの正解ではない。読者層（クラウド／AI／業務プロダクト寄りなど）によって最適は変わる。車載ハード読者には分量・スクショ比率の調整が必要。
- Zenn の仕様・反応の多少は時点で変動する。統計はこのメモ作成時点のスナップショット。
