# 車のバッテリー上がり対策に、車載 IoT を自作した話① 基板設計・作成編

## このシリーズについて

車のメイン／サブバッテリーを Cat-M（SORACOM）経由で AWS IoT に送り、遠隔で監視・設定する自作 IoT の記録。売りはハード〜ファーム〜クラウドの一気通貫。記事は分野ごとに 3 本に分けている。

| # | 編 | 内容 |
| --- | --- | --- |
| ① | **本編** | 動機・既製品 MVP・専用基板・試作／再設計・筐体 |
| ② | ファームウェア開発編 | 計測サイクル・OTA・キッティング・GHA |
| ③ | インフラ編 | Terraform・Grafana・Shadow／Jobs・運用コスト |

日常の閲覧は別プロジェクトの Grafana（EC2 上 Docker）。閾値変更などは Device Shadow / IoT Jobs。

---

## やりたいこと

車のメインバッテリーを何度か上げてしまった。
サブバッテリーやソーラー側の状態が分からないまま、メイン側を取りこぼして落ちる感じだった。

欲しかったのは次のようなものだった。

- メイン / サブのバッテリー電圧を遠隔で同時に見たい
- サブバッテリーの充電量（電流・電力・積算 Ah）も追いたい
- 車の近くで Wi-Fi が取れなくても動いてほしい
- 閾値を変えたり、ファームを直したりを手元で完結させたい

市販のバッテリーモニターもあるが、「LTE でクラウドに残す」「設定をリモートで変える」「自分でハードまで直す」まで含めると、作った方が早いと判断した。

## 既製品で MVP 作成

まずは「測れる・送れる・見える」を最短で確認するため、M5Stack の既製品で組んだ。

| 部品 | 役割 |
| --- | --- |
| M5Atom S3 | MCU（ESP32-S3）・簡易 UI |
| M5 Unit VMeter | ADS1115 ベースの電圧計測（**実質 1ch**） |
| M5 Unit CatM（U128 / SIM7080G） | SORACOM Cat-M で MQTT |

Grove ケーブルでつなぐだけで、車載 12V → 分圧 → ADS1115 → UART LTE → AWS IoT Core、という一連の経路が通る。
この段階のファームは `m5atom_iot_gateway` として残してあり、BLE の SwitchBot 温湿度 / CO2 もついでに拾える構成だった。

ただし試作（MVP）段階では制約・懸念がはっきりしていた。

- **ADC が 1ch** なので、メインとサブを同時監視できない（どちらか一方の電圧だけ）
- **サブバッテリーの充電量監視もできない**（電流計・積算 Ah がない）
- **DeepSleep 中も Cat-M モジュールの電源が入りっぱなし**で、サブバッテリーの消費電流が多かった

経路とクラウドの運用テストには十分だったが、「本当に欲しい監視」や車載常設の消費には届かない。ここが専用基板（2 系統電圧＋INA228、LTE 電源を GPIO で切る）へ進む動機になった。

ポイントは「最初からクラウド前提で組む」こと。
ローカル表示だけだと後で全部作り直すことになるので、MVP の時点で MQTT over TLS まで乗せることにした。

受信側（Terraform・S3・Athena。閲覧用 Web も同時に用意した）も MVP とほぼ同時に立ち上げ、実データを流して経路を証明した。いまの日常閲覧は Grafana 側で、詳細は **③インフラ編**。
この時点で「クラウドはもう使える。あとはハードをちゃんとする」という気持ちになれた。

## 自作基板の機能概要

専用基板を入れた結果、ユーザー（自分）から見てできることはだいたい次のとおり。

| できること | 内容 |
| --- | --- |
| 電圧の同時監視 | メインとサブの電圧を同時に遠隔で見る |
| 充電量の把握 | サブの電流・電力・積算 Ah（ざっくり残量）を追う |
| メインへの充電制御 | サブからメインへ充電する／閾値で自動開始・停止する |
| 現地での設定・確認 | OLED＋ボタンで Ah オフセットやセンサー表示、デバイス ID 確認など |
| リモート設定 | 充電閾値などを手元に行かずに変える（Shadow／Jobs。詳細は②③） |
| 常設しても食いすぎない | DeepSleep 中は通信モジュールの電源も落とし、サブの無駄食いを抑える |
| リレー制御（おまけ） | 外部リレーを GPIO で駆動できる口も付けてみた |

MVP では「片側の電圧だけ・充電量なし・通信が常時通電」で足りなかった。それを埋めるのが基板自作の目的だった。リレーは必須機能というより、ついでに口を空けておいた、くらいの位置づけ。どう回路で実現したかは次節。

## 回路設計・部品選定

既製品スタックはケーブルが多く、車載常設には心もとない。加えて MVP では **1ch 電圧しか取れず、サブの充電量も見えず、DeepSleep 中も Cat-M が常時通電**だった。
そこで KiCad で専用基板を設計し、**JLCPCB の PCBA 前提**で部品を選ぶことにした。

主なブロックは次のとおり（詳細はリポジトリの `m5atom_power_adc/CIRCUIT.md`）。

| ブロック | 内容 |
| --- | --- |
| 電源部 | ポリヒューズ + TVS → LM2596（12V→5V）→ AMS1117×2（3.3V デジタル / 3.3VA アナログ）。USB-C 受電との OR 接続もあり |
| ESP32 / デジタル部 | ESP32-S3-MINI-1 基板直付け、ブザー、デバッグ用 UART など |
| リレー接続部 | 外部リレー向けコネクタ、NPN ドライバ、コイルセンス |
| Grove 周辺 | LTE（SIM7080G）用 Grove、予備 Grove。GPIO からのパワースイッチで DeepSleep 時に遮断可能 |
| 電圧・電流計測（アナログ） | ADS1115 + 分圧（メイン／サブ 2 系統、差動）、INA228 + 外付けシャント（サブの電流・電力・Ah） |

MCU は当初 M5Atom 外付け案もあったが、最終的に **ESP32-S3-MINI-1 を基板直付け（カステレーション）** に確定した。
Grove 1 本運用より配線が減り、リレー制御やセンシングもまとめやすい。

部品はデータシートの参考回路をベースに定数を決め、JLCPCB / LCSC で揃う品番に寄せた。
分圧は 1% 品必須。

同じ回路を複数置く箇所（Grove 周辺、リレー接続部など）は、**KiCad の階層シート**にして回路図を使い回せるようにした。チャンネルを増やすときにコピー＆ペーストで定数がズレる、という事故を減らせる。

## 基板設計

回路が固まっても、レイアウトを雑にすると電圧計測がすぐガタつく。
PCB では大きく **ノイズ対策** と **電流に応じたトレース幅** の2点を意識した（`m5atom_power_adc/HARDWARE.md`）。

前章で入れた階層シートでは、**部品番号を階層と紐づけて採番**した。同じサブ回路（Grove やリレー接続など）ごとに Ref が揃うので、片方で詰めた **PCB レイアウトも流用・横展開しやすくなる**。回路図の再利用だけで終わらせず、パターンまでコピーしやすくする、という意図。

### ノイズ対策

#### ゾーン分離

- スイッチング領域（LM2596 / L / ダイオード）とアナログ領域（ADS1115・分圧）を離す
- ADS1115 は DC-DC の反対側へ置く
- GND はベタにしつつ、ノイズ領域とアナログは可能な限りスター結合っぽく扱う

#### フェライトビーズによる電源分離

**デジタル用 3.3V とアナログ用 3.3V は電源レールを分けた。**
どちらも同じ種類の LDO（AMS1117-3.3）で 5V→3.3V を作るが、IC を2個にして用途を分ける。デジタル用は ESP32 など向け、アナログ用は ADS1115 など向け。アナログ側の入力は +5V バスからフェライトビーズ経由にし、スイッチング／デジタル系のノイズが計測系に乗りにくいようにしている。

#### ループ面積の最小化

スイッチングノード（LM2596〜D〜L の三角ループ）は一番ノイズを飛ばす。
パターンを短く・小さく保ちつつ、流れる電流に見合うトレース幅も確保する——**面積最小化と配線太さの両立**を意識した。

### 電流に応じたトレース幅

1oz 銅箔での目安。

| 用途 | 電流の目安 | トレース幅 |
| --- | --- | --- |
| +12V / スイッチングノード | ~1A | 1.5mm |
| +5V バス | ~500mA | 0.8mm |
| +3.3V デジタル | ~350mA | 0.5mm |
| アナログ・信号 | 数 mA | 0.3mm |

## 試作

設計を JLCPCB に流し、PCBA 付きで発注。到着して通電すると……**抵抗が焼けた**。

原因は単純で痛い。いくつかの抵抗の定数指定をミスしていて、**100kΩ のはずが 100Ω（`k` が抜けていた）** になっていた。
車載 12V をそのまま近い経路に食わせると、所定の分圧・保護にならない電流が流れ、チップ抵抗が一発で逝く。

机上レビューでは見落としやすく、実機通電で一気に可視化されるタイプのミスだった。

---

## 再設計

焼けた原因は BOM / 定数の打ち間違いだったので、**部品リストを洗い直して再設定**した。

通電直後に黒コゲまで行った個体だけではない。見た目は無事でも、おかしいところがある。そこで **サーモカメラ** が役に立った。
設計上そんなに熱くなるはずのない箇所が、サーモでははっきりホットスポットになっている。その周辺の定数を追うと、やはり `k` 抜けなどで電流が流れすぎている抵抗が見つかった、というパターンもあった。
目視やテスタだけでは拾いにくい「静かに間違っている部品」を、発熱という結果から逆算できた。

あわせて次も実施した。

- 抵抗値の桁（k / なし）を全数見直し
- 定格・パッケージ・ピン互換の再確認
- 保護・分圧・駆動まわりの定数再確認
- 改訂後 BOM で再発注

完璧な一発正解を狙うより、「壊せる試作で学ぶ → BOM を正す → 次ロット」の方が速い、というのがこのフェーズの学び。
再設計後の基板は、本番投入にはまだ足りない部分があっても、ファームを書くのに十分な土台になった。

## 筐体設計

基板むき出しのまま車に置くのは不安なので、試作基板の寸法をベースに筐体を設計した。
CAD は Fusion 360 の個人用途ライセンスを利用。

コネクタ・LTE モジュール・通気・固定穴・ボタン／OLED の取り回しを実機合わせで詰めていくと、基板シルクソロだけでは分からない干渉が出てくる。
「ファームが動く試作基板があるから筐体が作れる」という順序でよかった、と振り返っている。
（動く試作＋OTA 前提のファーム側の話は **②ファームウェア開発編**。）

## この編のまとめ

- 動機はメインバッテリー上がり。メイン／サブ同時監視とサブの充電量監視、リモート設定まで自作する方針にした
