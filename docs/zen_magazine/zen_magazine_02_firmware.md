# 車のバッテリー上がり対策に、車載 IoT を自作した話② ファームウェア開発編

## このシリーズについて

車のメイン／サブバッテリーを Cat-M（SORACOM）経由で AWS IoT に送り、遠隔で監視・設定する自作 IoT の記録。売りはハード〜ファーム〜クラウドの一気通貫。記事は分野ごとに 3 本に分けている。

| # | 編 | 内容 |
| --- | --- | --- |
| ① | 基板設計・作成編 | 動機・MVP・専用基板・試作／再設計・筐体 |
| ② | **本編** | 計測サイクル・OTA・キッティング・GHA |
| ③ | インフラ編 | Terraform・Grafana・Shadow／Jobs・運用コスト |

日常の閲覧は別プロジェクトの Grafana（EC2 上 Docker）。閾値変更などは Device Shadow / IoT Jobs。  
①で再設計した試作基板を土台に、本番相当のファーム `esp32_iot_gateway` を育てていく話。git を振り返ると「まず動く骨格 → OTA で車に行かない開発へ → 運用・通信量に耐える」の順で厚みが増えた。

## 骨格：3 層構成とキッティング前提

ビルドは **PlatformIO** を採用した。理由は、依存ライブラリの管理がやりやすそうだったから。Arduino IDE だと版の揃えや複数プロジェクトの扱いが雑になりがちで、`platformio.ini` で env を分けられるのも後の develop / release 分離に効いた。

アクティブな開発は `esp32_iot_gateway`。初期実装のあと、早めに **device / domain / service** の 3 層へ切り直した。

| 層 | 役割のイメージ |
| --- | --- |
| device | ADS1115 / INA228 / LTE（SIM7080G）/ OLED / ボタン / BLE などハード直結 |
| domain | 計測値やテレメトリの形（ペイロード組み立て） |
| service | MQTT・OTA・Jobs・Shadow・メニュー・オフラインキューなどユースケース |

ほぼ同時期に、**デバイス固有情報をファームから分離**し、キッティング前提にした。
理由は単純で、**OTA を S3 の公開バケットで配るため**。バイナリに証明書や device_id が入っていると公開配信できない。
なので証明書は `certs.h` 埋め込みをやめて SPIFFS（`/certs/`）へ、device_id・MQTT ホスト・証明書 CRC などは NVS 管理にした。公開バイナリと個体情報を混ぜない土台は、ここで先に決めてある。

## 計測サイクルと DeepSleep

ざっくりした起動〜1 サイクルは次のとおり。

1. 周辺初期化（ADS / INA228 / OLED / ボタン / BLE など）
2. LTE 接続（SIM7080G）
3. **OTA / Jobs チェック**
4. 計測 → MQTT publish → Shadow reported
5. LTE 切断 → DeepSleep（おおよそ 5 分）へ

DeepSleep まわりでは、後から次のような実践が入った。

- **次の UTC 5 分境界に合わせて寝る**（タイムスタンプが揃い、グラフも読みやすい）
- **LTE 圏外時はオフラインバッファ**（まず RTC、必要なら SPIFFS に残し、復帰後に flush）
- release ビルドでは DeepSleep 前にモデム電源を落とし、①で挙げた「Cat-M 常時通電」問題を潰す

ペイロード例（短縮キー。ingest Lambda が展開して S3 に保存）:

```json
{"t":"battery","m":12.34,"s":12.10,"i":5.2100,"p":62.500,"tp":28.5,"ah":200.001234,"ts":1746143400}
```

## OTA を最優先で固めた

なぜ最優先にしたか。理由は単純で、**車までモジュールを取りに行くのがめんどくさいから**。
USB 書き換えのたびに車へ行く開発サイクルは続かない。

ジョブは AWS IoT Jobs。デバイスは起床時に `$next` を取りに行き、あれば HTTPS でファームを落として app0/app1 の 2 スロットに書く。起動後に MQTT が確認できなければロールバックする。

実装も一度では終わっていない（だいたいこの順）。

1. SIM7080G の MQTT URC 形式に合わせて、まず **OTA を疎通**
2. ダウンロードを **AT+HTTPTOFS → CFSRFILE** の流れに刷新（モデム FS 経由）
3. OLED に進捗表示、失敗時メッセージ
4. **gzip 圧縮配布**（uzlib で解凍。のちストリーミング解凍で高速化）
5. Jobs プロトコルを共通化し、**OTA とコマンド（Ah リセット・充電など）を別レイヤー**に分離

「OTA がある」から「車載のまま短サイクルで直せる」までの道のりが、この編の中核だった。

## GitHub Actions で配布まで自動化

OTA 本体だけでは運用は回らない。**ビルド〜配布〜ジョブ作成**まで自動化した。

`vX.Y.Z` タグを push すると GitHub Actions が:

1. release 用 env でファームをビルド
2. `firmware.bin.gz` を生成して **公開可能な firmware 用 S3 バケット**へ配置
3. IoT Jobs ドキュメントを生成・アップロード
4. Thing グループ `ota-target-car-iot-gw` 向けに OTA ジョブを作成
5. GitHub Release にバイナリを添付

という流れ。AWS 認証はアクセスキーではなく **OIDC**。OTA 対象は Thing 単位ではなく **グループ所属**で制御する。

ここで大事なのは、やはり **秘匿情報とデバイス固有情報をファームバイナリに焼かない**こと。

- 証明書・秘密鍵・MQTT ホスト・device_id・基板バージョンなどは、初回キッティング（`ops/provision_device.ps1`）で SPIFFS / NVS に書く
- 公開バケットにはバイナリ本体だけ置く
- 認証は AWS IoT 側のデバイス証明書で担保する

「ファームは全員同じ URL」「個体差はキッティング」。DeepSleep 中の端末は、次の起床で Jobs を拾って自動更新する。

## 通信量削減：短縮キーから MessagePack へ

Cat-M は帯域が細い。ペイロードは二段で絞った。

1. **Phase 1**: JSON のフィールド名を短くする（`main`→`m` など）
2. **Phase 2**: **MessagePack** 化（実測おおよそ **59 bytes**。旧 JSON 比で数割減）

短縮名は FW の通信まわりに閉じ、ingest Lambda が展開して S3 にフルネームで書く。Glue / Athena / Web はほぼ触らずに済む、という分け方にした。

## 現地メンテとリモート設定

車のそばで触る用に、**OLED + 2 ボタンの階層メニュー**を入れた（Ah オフセット、センサーリアルタイム表示、デバイス ID の QR、NVS クリアなど）。

クラウド側から触る用には、Shadow を「テレメトリ置き場」から **設定値（desired / reported）** に刷新した。充電開始・停止電圧などはここ経由。Jobs コマンドで Ah リセットや充電指示も飛ばせる。
（管理画面 UI の話は **③インフラ編**。）

## 展望：基板 v2（開発中）

いま運用しているのは v1 系。次のハード改訂として **基板 v2 は開発中**で、ファーム側だけ先に仕込み始めている。

- **ピン差の吸収**: ピン定義を `board_pins`（v1 / v2）に寄せ、キッティング時に `board_version` を NVS へ書く。ハード改訂のたびに `#ifdef` 地獄にしないための準備
- **自己保持（PWR_HOLD）**: v2 では電源ボタン＋自己保持回路を入れる想定。FW では起動直後の HIGH アサートや DeepSleep 中の GPIO hold など、保持に必要な処理を v2 向けに入れ始めている（基板そのものはまだ開発中）
- **能動的な電源断（未着手）**: メイン電圧が危機的になったとき、PWR_HOLD を落として **回路全体の電源を断つ**判定ロジック。メインバッテリー上がりの安全ネットとして置きたいが、ここはこれからの話

①のハード編で書いた動機（メイン上がり）に対する、次ロット寄りの答えが v2、という位置づけ。

## この編のまとめ

- 3 層構成＋証明書のキッティング分離を早めに入れた
- 計測 → Jobs/OTA → MQTT → DeepSleep。圏外バッファや 5 分境界スリープで運用を安定させた
- **OTA を最優先**したのは、車まで取りに行くのがめんどくさいから。gzip・Jobs 分離・GHA まで積み上げた
- MessagePack で通信量を削り、メニューと Shadow で現地／リモートの両面を持たせた

シリーズはハード／ファーム／インフラに分けている。OTA・キッティング・Cat-M まわりだけ欲しい人は、この編だけでも読んでほしい。
